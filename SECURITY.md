# Browser studio security

ARTFORGE processes imported media in the user's browser. The hosted application serves a fixed set of static files; it does not accept uploads, proxy URLs, run commands, or decode media on a server. The simulated spamware windows are canvas artwork.

## File handling

- All image entry points (source, spam image, image layer, and embedded project images) use the same byte-level validation and cleanup. File names and browser-supplied MIME types cannot authorize an image decoder.
- PNG, baseline/progressive JPEG, GIF first frames, and static WebP are supported. SVG, HTML, XML, documents, unsupported raster formats, and disguised non-image files are rejected.
- Container bounds and dimensions are checked before decoding. PNG chunk checksums are validated. Image comments, ancillary metadata, compressed profiles, extra animation frames, and trailing bytes are discarded. JPEG orientation is reconstructed in a minimal EXIF record; other EXIF content is discarded. Accepted images become canvas pixels, and saved image layers use fresh PNG encoding.
- Images: 24 MB maximum, 8192 pixels per edge, 32 million source pixels. Source canvas is limited to a 2560px edge; overlays to 1920px. Projects are at most 64 MB and 16 layers; imported image layers have a combined 24-million-pixel budget. Embedded image URLs must be bounded base64 raster data, never remote URLs.
- Videos: MP4/WebM only, at most 200 MB and one hour; decoded dimensions are checked. Audio has a 50 MB/one-hour limit. Playlists are rejected. The converter explicitly enables only MP4/WebM parsers, drops source container tags, and bounds output dimensions to 1280px.
- Text, file names, and recipe names are rendered with `textContent`, form values, or Canvas text APIs. Imported values do not enter HTML templates, JavaScript, CSS rules, or module paths. Project data is copied through allowlisted validators rather than merged into application prototypes.

## Browser and hosting controls

The hosted Worker is generated by `node scripts/build-hosted.mjs`. It accepts only GET/HEAD requests for bundled paths. Unknown routes and other methods receive fixed error messages. There is no upload API or arbitrary file path lookup.

Responses include a restrictive Content Security Policy, `nosniff`, clickjacking protection, HSTS, no-referrer, opener/resource isolation, and a device Permissions Policy. Inline JavaScript, JavaScript eval, external network connections, frames, plugins, forms, and base-URL overrides are blocked. The policy permits same-origin modules and fonts, local blob media/workers, and WebAssembly compilation needed by the bundled AAC encoder; it does not enable JavaScript `unsafe-eval`. The HTML also contains a CSP fallback for simple local static servers.

Rendering dependencies are pinned and vendored. No third-party runtime CDN, analytics, or user-media upload is part of the application. Hosting providers may apply their own delivery/security services. Dependency versions and licenses are in `web/vendor`.

## Recording reliability

Silent image loops do not initialize audio. Audio startup, seeking, decoding, recorder completion, and MP4 packaging have time limits. Recording stop deadlines are installed before playback starts. A missing recorder stop event releases tracks and recovers available chunks. MP4 packaging can be cancelled; raw recording recovery remains available. A persistent download link provides a manual save action when a browser blocks an automatic download.

## Verification and limits

`npm test` includes malformed image headers, excessive dimensions, embedded SVG/HTML, appended payloads, project URL rejection, prototype keys, host method/path restrictions, header coverage, recording deadlines, manual stop, and recorder recovery. Run the browser import/export checks after changing media or security code. Run `npm audit --omit=dev` when reviewing/updating bundled dependencies.

These defenses reduce attack surface; they are not antivirus certification or a guarantee of zero vulnerabilities. Pixel steganography is still pixel data, and cleanup does not prove that all malicious content is absent. Browser/OS decoder flaws, WebCodecs bugs, resource exhaustion within allowed limits, dependency vulnerabilities not yet disclosed, and hosting/account compromise remain possible. Keep browsers and operating systems updated. The legacy/local terminal tool has a separate trust boundary; these browser checks do not sandbox Python, Pillow, or FFmpeg on a user's computer.

Reference guidance: [OWASP file handling](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), [MDN Content Security Policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy).
